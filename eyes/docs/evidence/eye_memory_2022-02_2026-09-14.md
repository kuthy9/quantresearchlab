# Eye memory on the 2022-02 tape, and what the day's fixes changed (2026-09-14)

Two questions. With per-bar time bounded
(`eye_growth_profile_2022-02_2026-09-14.md`), what still grows in memory
across a month of 1m replay, and does any of the day's fixes — A1–A4, B1,
B2, the checkpoint verifier, the journal, the bounded bar memories, the
forward-reference change — alter what the Eye publishes?

Tape: `data/processed/nq_1m_previous_session_front_v2_3_2017_2026.parquet`,
2022-02-01 → 2022-03-01 (27,360 completed 1m bars, 370,886 events),
`configs/model.json` as registered. Baseline: commit `b580b9d`, the last
commit before A1, in a temporary worktree. Every number below is copied
from a script's log; the scripts were scratch (`canon_stream.py`,
`canon_all.py`, `canon_multiset.py`, `probe_reach.py`, `compare_hash.py`,
`compare_census.py`), built on `eyes/scripts/replay_hash_stream.py` and
`eyes/scripts/replay_coverage_stats.py`.

## Does the Eye publish the same thing?

Identifiers move on purpose: B2 registered a Group 3 parameter, so the zone
and interaction protocol hashes changed and with them every FVG, OB and
interaction identity and every event id derived from one, and
`semantic_registry_identity` moved from `f43563d2…` to `144f1d6c…`. So the
comparison renames every 24- or 64-hex id by first appearance in each run
and masks the protocol hashes and the registry identity; two runs whose
only difference is id derivation then compare equal.

**Events, first week (6,900 bars, baseline vs HEAD).** Raw
`content_hash(events)` differs on 810 bars, the event count on none; after
renaming, the semantic events are identical on all 6,900 bars. The first
raw divergence (bar 69) is an FVG's `protocol_hash`, `entity_id`, and the
event ids citing it — nothing else.

**Events, whole month (27,360 bars, baseline vs HEAD).** Same event count on
every bar (65,539 semantic events; 370,886 events on the audit log). After
renaming, the semantic events are identical on 27,358 bars. The two
remaining bars (8,167 and 8,735) each carry one `liquidity_retired` whose
`sequence_no` is 4,000,000 on the baseline and 4,000,001 on HEAD; the event
id, content, and order are the same. `EventMemory.append` numbers events
per `observed_at` and `sync_retained_entity_timelines` prunes that clock
table to the clocks still held by a retained timeline or a recent event —
in the middle of an update. On the baseline the prune fired between the
bar's `bar_completed` and its retirement and reset the clock's counter; on
HEAD the swing timelines cool (A2), the table is smaller, and the prune
fired on other bars where nothing else was appended at that clock. The
baseline's number is the anomaly (two events at one clock both numbered 0
in their channel); HEAD's is the one `append` documents.

**Every event on the audit log, whole month** (`market_snapshot.events_this_update`,
370,886 events, typed-state transport included). Masking every id, the
protocol hashes, the registry identity and `sequence_no`, and comparing
each bar's events as a multiset: identical on all 27,360 bars. Keeping
order and `sequence_no`: 212 bars differ — 29 are the retirement channel's
`sequence_no` one higher on HEAD (`liquidity_retired` and
`level_invalidated` at floor 4,000,000; the same mid-update prune as
above, always +1, never the reverse), and the remaining 183 are the
`entry_path_state` transport events of one update in a different order
(their ids follow the interaction protocol hash, and the order follows the
ids; a raw dump of bars 520 and 805 shows no field differing apart from
the permutation and the ids).

**Observations.** `content_hash(observation)` differs on every bar from bar
0 (`semantic_registry_identity`, `event_prefix_fingerprint`). Sampling every
250th bar of the first week and comparing by entity id: the only records the
baseline has that HEAD lacks are FVG and OB states in a terminal lifecycle
(`mitigated` 2,377, `invalidated` 2,095, `failed` 20 across 28 samples) —
B2's compaction of exposed terminals — and the same ids in Group 5's
`cold_source_ids`; HEAD adds no record, and no record present in both
differs. After dropping those, 27 of the 28 samples are isomorphic under an
id bijection; the 28th differs only in three `micro_break_facts` whose
`reference_id` follows the interaction protocol hash (verified against the
raw dump: every differing field is a protocol hash or an id derived from
one).

**Census sections.** `eyes/scripts/replay_coverage_stats.py` on HEAD against
the JSON it wrote before the day's fixes: `ranges`, `formation_clock`,
`target_outcomes`, `event_clock` and `scales` identical; the checkpoint
event totals identical (67,243 / 135,514 / 203,457 / 271,212 / 338,172 /
370,886). `duplicates.exact_same_update_extra` fell from 20 to 0: the
census's duplicate key includes the events' source ids, and the twenty
`displacement_observed` pairs that shared every key field on the baseline
cite ids that B2's protocol hash now derives apart; the multiset
comparison above shows the events themselves unchanged.

**A pre-existing bug the checkpoint work found.** Restoring a reducer or
publisher checkpoint taken after the first settled Swing failed
("compact checkpoint failed replay") at `b580b9d` and `a52241f`: the
publisher persists geometry views and candidate rank projections into the
reducer state, and a cold fold never reproduces them. Fixed in `434f6cc`
by verifying the fold-owned part of the state; the projections travel in
the checkpoint bytes.

## Where the memory went, and what is bounded now

Before the journal, the audit store held every event object of the run in
three maps: about 2 KB per event on the heap, 26 MB per 1,000 bars, a
gigabyte a month. With `audit_journal_dir` set the observer spills committed
events older than `audit_hot_window_minutes` to an append-only file and
keeps 32 bytes of digest and one id→index entry per cold event. On the
month: 346,271 of 370,886 events cold at the end, 480 MB on disk (1.39 KB
per event), hot events between 18,000 and 57,000 depending on where the
three-day window falls against the weekend. Each observer opens its own
uuid-named journal under `audit_journal_dir` and nothing removes it — a
checkpoint may still name it — so the day's eight replays left 2.0 GB
under `outputs/eye_journal`; a lifetime rule for journals is an open item.

window fixed when the reader forms: the emitter's close and range per bar
root and each scale's clock-ordered root list (32,768), the store's
eligible-bar index (4,096 per scale) and same-clock reservations (8,192).

No lookup missed. The per-entity memories are read over the whole run: the
emitter re-walks every retained entity on every frame (3.7 M penetration
lookups a month for 20 K entries), so an entry is read for as long as the
slowest scale retains its entity, and 256 retained 4H swings is months. A
count bound there evicts entries that are still read, and every reader
fails closed — some by raising, most by publishing the event without the
citation. The four bar-keyed memories at the bottom of the table are read
within a window fixed when the reader forms (a Swing's own confirmation
window, the next root of the crossing's scale, the once-per-BOS raw break)
and are the ones kept bounded.

The per-entity memories cost about 75 MB a month of 1m tape (140 K string
entries and 20 K retained terminal-crossing event objects) when nothing
drops them. They now follow retention — next section.

## Per-entity memories follow tracker retention (2026-09-15)

An entry is read for as long as some tracker retains its entity or another
entity that cites it, and no longer. Whenever the memories have doubled
since the last pass (above 65,536 entries) the observer harvests every
identifier field from the tracker states it publishes — frames,
displacement, inventory, pools, interaction, Group 4 — plus the reducer's
candidate set and its own inventory bookkeeping, and the emitter drops
every entry none of them names (`eyes/core/entity_liveness.py`,
`SemanticEventEmitter.prune_entity_memories`).

Three harvests were tried on the month, each with a tombstone on every
dropped key so that any later read of one is logged, and the full audit
log compared with the baseline as an id-masked multiset:

| harvest | passes (bar: dropped → entries left) | live ids | tombstone reads | log vs baseline |
|---|---|---|---|---|
| everything published, keys matched as stored | 9,734: 44,811 → 20,732; 16,383: 32,407 → 33,131; 21,402: 24,376 → 41,897 | 24,927 → 38,379 | 14,382 (`_known_level_touch_ids`) | identical |
| same, keys also matched on their bare id | 9,734: 13,064 → 52,479; 17,501: 11,110 → 93,853 | 24,927 → 33,900 | 0 real | identical |
| tracker states + reducer candidates only | 9,734: 48,650 → 16,893; 16,943: 38,277 → 27,277; 22,760: 30,827 → 34,712 | 3,988 → 4,873 | 0 | identical |

The first harvest dropped touch identities of swings that were still in a
frame: the frames cite the bare swing id, the memory keys `swing:…`, and
the rediscovered touches were re-appended and deduplicated by content —
identical output by luck, not by design. The second matched keys on their
bare id but harvested the reducer's states too, whose swing hierarchy holds
2,048 swings per scale, so most entries survived. The third is what ships:
the emitter never reads the reducer's states except for the candidate set
whose retirements it publishes, and with those the live population is
about 5,000 ids and the memories after a pass are the candle-id window
(32,768) plus a few thousand entries. Zero tombstone reads across 27,360
bars; 370,886 events identical to the baseline's as a multiset on every
bar. `test_entity_memory_pruning.py` proves the same on two sessions with
a pass at every doubling above 256 entries.
